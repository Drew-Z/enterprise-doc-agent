## 本地代码定位

- `apps/worker/src/enterprise_doc_worker/consumer_main.py` 的 `main` / `build_consumer_app`
  是实际 Celery consumer 装配入口，创建 durable Agent handler 并调用 `app.worker_main`。
- `apps/worker/src/enterprise_doc_worker/__main__.py` 的 `run_worker` 负责 probe、lifecycle 和
  Outbox publisher。其注册 task 的事实不能单独证明这个进程实际消费了某次 Job。
- `apps/worker/src/enterprise_doc_worker/agent_handler.py` 的 `AgentExecutionHandler.__call__`
  包装 executor 异常，记录 `agent_execution_handler_failed` 并产生 `AgentExecutionRuntimeError`；
  `_agent_failure_diagnostic` 对已分类错误保留既有语义，对未分类异常使用有限类型分类。
- `apps/worker/src/enterprise_doc_worker/queue.py` 的 `JobDeliveryConsumer._settle_handler`
  将 handler diagnostic 交给 durable `runtime.fail`；任务持久化中的外层异常名不等于底层异常类型。
- `apps/worker/src/enterprise_doc_worker/config.py` 的 `WorkerServerSettings.worker_id`
  默认是 `worker-local`。当前没有可用于本次历史 attempt 的唯一执行进程标识。
- `scripts/staging_smoke.py` 在 Agent 未成功时抛出 `StagingSmokeFailure`；`main` 只在
  `run_staging_smoke` 正常返回后写成功报告。这解释本次 smoke JSON 缺失，不能解释 QA 根因。

## 下一步的证据与修复边界

1. 优先查询可用的历史执行端、数据库或日志平台记录，将同一 run/job/attempt 与实际进程绑定。
   使用现有精确窗口及关联值，仅在内存中处理标识，不下载文档、提示词、模型输出或凭据。
   没有可靠证据时继续保留 `inconclusive`，不将外部执行端或提供方超时写成事实。
2. 如需补观测，先设计独立的本地离线复现：经真实 consumer 启动和 durable attempt 边界触发
   合成故障，证明进程来源、结构化日志和持久化诊断可对齐。外部模型/MCP 调用必须禁止；
   唯一进程标识不能成为 Prometheus 的高基数标签。发布前需审阅准确改动和验证结果。
3. 另行评审 smoke 失败报告契约：失败也写出脱敏阶段和终态，进程仍返回失败，发布 record
   仍拒绝不通过的 gate。覆盖 Agent failed、超时、上传失败及诊断缺失，避免通过降低验收要求
   取得绿色工作流。当前仅定位了报告缺口，尚未修改脚本或测试。
4. 没有新授权时不执行第三次部署、回滚、新 12/40 例 RAG trial，或通过真实模型反复试跑找原因。
   提交清单在 [部署计划](../../../../docs/ops/v0.1.34-staging-deployment-plan.md#本轮归档提交边界)，
   本次使用的部署批准没有覆盖新增归档的提交和推送。
