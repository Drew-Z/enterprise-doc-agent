## 获准切换后的阶段顺序

1. **开窗前核对。** 读回 namespace UID、配置摘要、运行镜像/副本、数据库版本和发布 manifest；任一项与批准清单不一致则停止。准备同一冻结写入窗口的 DB 与对象恢复点，放入当前集中恢复组；9 月 25 日历史快照不能充当本次切换前备份。
2. **暂停新业务并排空。** 采用经审阅的维护入口/停止 API、Web 提交，确认外部 MCP/其他写入方也停止。Worker/Consumer 只完成既有任务，禁止补发历史失败。核对 jobs 的 pending/retry_wait/running、Presales 的 running/queued/recovering，以及 Agent 的 pending/running/waiting_approval 和活动上传；有旧版可恢复任务时先处理，不清空队列或改写状态来凑零。本次四条 running 工具和一条 writing 产物均重新确认属于已失败且无活动租约的历史任务，保留原状态与对象。下一窗口仍须重新核查，不能复用本次排空结论。
3. **备份与迁移。** 核对完整恢复点哈希后，以候选 migration Job 升至 `20260924_0031`。保留原有迁移 Job 成败、实际版本和耗时；失败或超时立即停止自动推进。不能把 Job 的超时等同于数据库没有提交。
4. **配置与应用。** 将经审核的有限企业额度、四组件发布摘要、GitHub/对象/向量原配置与显式功能开关一起固定。使用已有 prerequisites 渲染/校验流程，保持管理员所有权，不扩大部署服务账号权限。四个应用按同一候选发布，Redis 和数据卷不重建；MCP 如由独立进程使用，也须同步到兼容版本或维持停用。
5. **保持维护，先读后写。** 验证 ready、登录入口及授权、历史文档/响应表读取、跨租户拒绝；核对实际 0031、镜像/配置与每个 Worker 的成功/时间戳。无真实供应商预算时不做真实上传解析/生成验证，也不对真实企业开启提交。
6. **受控业务验收后恢复服务。** 本次使用已批准试点企业和固定 172 字节合成 TXT，按 1/18/0 调用上限完成上传、解析、同步生成、复核、CSV 与同键重放，确认一次结算后才开放 Web。交互式 OAuth、浏览器断网恢复及绑定业务阶段的两轮容量试验仍待验收，后者按 [4C4G 方案](4c4g-business-capacity-plan.md) 执行。此次功能通过不等于商业准入完成。

本次从暂停请求到公网恢复验证为 1727.5 秒，约 28.8 分钟；arm 到迁移 claim 为 1112.1 秒，在 1500 秒截止前。首次维护超时停机 185.8 分钟的失败记录仍保留。现有 workflow 的迁移 Job 上限 2700 秒、Worker 等待 1800 秒、单次流水线 90 分钟都是终止上限；单次成功时长不构成停机承诺，也不证明自动恢复或整机 RTO。

## 按失败阶段回滚

| 失败位置 | 允许的恢复动作 | 不允许推断 |
| --- | --- | --- |
| 尚未改数据库、尚未换镜像 | 核对仍为 0027 与原模板/配置后，恢复记录的原服务副本；保留完整失败回执 | 单凭 workflow 失败就认为 DB 未变 |
| 迁移失败、取消、超时或版本未知 | 保持维护及暂停状态，读实际版本/Job；在隔离副本判断向前修复方案 | 自动 apply 候选、直接 rollout undo 或自动 downgrade |
| 已到 0031，候选尚未开放写入 | 使用 rc.0 / `93d95a9…` 的已验证摘要并保留 0031；本机实际镜像回退已通过，正式配置及 Kubernetes 切换仍须按批准执行包核验 | v0.1.44 可无条件读取新 JSONB 前提和新账本，或本地演练等同正式回滚验收 |
| 候选已产生新业务/供应商历史 | 停新提交、保留在途任务、冻结和核对新历史；关闭新功能并切到已验证兼容候选或向前修复 | 恢复旧快照后仍无数据损失、回滚消费/费用为零 |
| 必须回到旧数据库快照 | 另行批准具体数据损失边界，隔离恢复 DB+对象并核对引用后切换；当前没有备用服务器 | 覆盖正式数据库或用旧对象快照伪装无损恢复 |

`rollback_release.py` 只处理 Deployment revision，不回退 ConfigMap、Secret 或数据库，也不验证业务数据读取兼容。表内 revision 是基线，不是当前即可执行的通用 rollback 指令。迁移 0028–0031 在存在后台/配额/供应商历史时会拒绝破坏性降级，应保留这些约束。

standard 工作流收尾只在 prerequisites、migration、workloads 全部为 success 时恢复**已应用候选**的副本；任何失败/取消/跳过/空值均无 kubectl 调用。maintenance 模式始终保留暂停，由获准恢复步骤处理。迁移 claim 后独立守卫永久禁止自动恢复旧代码，必须核查实际版本；该 `0027` 恢复计划不能直接用于现已为 `0031` 的下一次维护。
