## 数据库与配置差异

| 迁移 | 主要变化 | 发布前须处理 |
| --- | --- | --- |
| 0028 | 售前后台状态、任务绑定、供应商调用及路由健康 | 排空旧版运行请求；新状态/调用历史不能被旧版覆盖 |
| 0029 | Agent 成功任务与文档处理配额、预留/结算事件 | 审核受邀企业及演示企业的有限额度；迁移本身不会为已有企业自动填入商业额度 |
| 0030 | 独立供应商 HTTP 尝试账本 | 旧版创建且尚未完成的任务必须先处理，避免跨版本执行缺少预留/记账 |
| 0031 | 供应商请求标识与对账索引 | 保留已有历史，禁止把未知 token/费用改成零 |

额度应通过 `manage_tenant_entitlements.py configure-products` 先预览，再以明确企业、当前 entitlement/version、Agent 任务数和文档字节数执行经批准配置。不要直接更新计数、重置额度周期或以无限额度解决升级后的拒绝。真实企业额度值尚未在本方案中批准。

第一阶段配置保持 `PRESALES__BACKGROUND_GENERATION_ENABLED=false`、`PRESALES__AUTOMATIC_FAILOVER_ENABLED=false`。现网这两个键缺省，新候选默认均为 false；发布包须显式写入，不依赖环境继承。运行采样保持 `OTEL__METRICS_ENABLED=true`。开启后台及切换属于后续受控试验的单独配置差异。

`deploy-staging.yml` 的 standard 模式仍会执行 embedding rollout，`run_smoke=false` **不会**使 standard 成为零供应商调用。新增维护路线要求管理员设置 `STAGING_DEPLOYMENT_MODE=maintenance` 且 `run_smoke=false`，先证明业务已停止、向量配置不变，再迁移及安装四个零副本应用；所有业务/供应商验证跳过且不会自动恢复服务。具体配置、有限额度、备份/停机/恢复步骤见 [维护部署执行清单](maintenance-deployment-runbook.md)。成功仅记录 installed_paused / blocked_external，不能当作上线验收通过。

## 获准切换后的阶段顺序

1. **开窗前核对。** 读回 namespace UID、配置摘要、运行镜像/副本、数据库版本和发布 manifest；任一项与批准清单不一致则停止。准备同一冻结写入窗口的 DB 与对象恢复点，放入当前集中恢复组；9 月 25 日历史快照不能充当本次切换前备份。
2. **暂停新业务并排空。** 采用经审阅的维护入口/停止 API、Web 提交，确认外部 MCP/其他写入方也停止。Worker/Consumer 只完成既有任务，禁止补发历史失败。核对 jobs 的 pending/retry_wait/running、Presales 的 running/queued/recovering，以及 Agent 的 pending/running/waiting_approval 和活动上传；有旧版可恢复任务时先处理，不清空队列或改写状态来凑零。然后停止 Worker/Consumer。当前只读计数不替代开窗前检查，也没有完成 Agent/上传全量排空验收。
3. **备份与迁移。** 核对完整恢复点哈希后，以候选 migration Job 升至 `20260924_0031`。保留原有迁移 Job 成败、实际版本和耗时；失败或超时立即停止自动推进。不能把 Job 的超时等同于数据库没有提交。
4. **配置与应用。** 将经审核的有限企业额度、四组件发布摘要、GitHub/对象/向量原配置与显式功能开关一起固定。使用已有 prerequisites 渲染/校验流程，保持管理员所有权，不扩大部署服务账号权限。四个应用按同一候选发布，Redis 和数据卷不重建；MCP 如由独立进程使用，也须同步到兼容版本或维持停用。
5. **保持维护，先读后写。** 验证 ready、登录入口及授权、历史文档/响应表读取、跨租户拒绝；核对实际 0031、镜像/配置与每个 Worker 的成功/时间戳。无真实供应商预算时不做真实上传解析/生成验证，也不对真实企业开启提交。
6. **受控业务验收后恢复服务。** 使用独立测试企业、固定合成文件、受控模型/向量执行全流程和浏览器断网恢复；必须证明任务/供应商账本没有重复结算。绑定真实主机、候选和业务阶段的容量试验另按 [4C4G 方案](4c4g-business-capacity-plan.md) 执行。获准窗口、目标、请求上限和模型预算记录齐全，才开放新业务；功能通过不等于商业准入完成。

停机时长尚未实测。现有 workflow 迁移 Job 上限 2700 秒、Worker 等待 1800 秒、单次流水线 90 分钟；这些是终止上限，不能当作可承诺的用户停机时间。发布前须选择实际维护窗口并在每阶段设操作停止点。

## 按失败阶段回滚

| 失败位置 | 允许的恢复动作 | 不允许推断 |
| --- | --- | --- |
| 尚未改数据库、尚未换镜像 | 核对仍为 0027 与原模板/配置后，恢复记录的原服务副本；保留完整失败回执 | 单凭 workflow 失败就认为 DB 未变 |
| 迁移失败、取消、超时或版本未知 | 保持维护及暂停状态，读实际版本/Job；在隔离副本判断向前修复方案 | 自动 apply 候选、直接 rollout undo 或自动 downgrade |
| 已到 0031，候选尚未开放写入 | 使用 rc.0 / `93d95a9…` 的已验证摘要并保留 0031；本机实际镜像回退已通过，正式配置及 Kubernetes 切换仍须按批准执行包核验 | v0.1.44 可无条件读取新 JSONB 前提和新账本，或本地演练等同正式回滚验收 |
| 候选已产生新业务/供应商历史 | 停新提交、保留在途任务、冻结和核对新历史；关闭新功能并切到已验证兼容候选或向前修复 | 恢复旧快照后仍无数据损失、回滚消费/费用为零 |
| 必须回到旧数据库快照 | 另行批准具体数据损失边界，隔离恢复 DB+对象并核对引用后切换；当前没有备用服务器 | 覆盖正式数据库或用旧对象快照伪装无损恢复 |

`rollback_release.py` 只处理 Deployment revision，不回退 ConfigMap、Secret 或数据库，也不验证业务数据读取兼容。表内 revision 是基线，不是当前即可执行的通用 rollback 指令。迁移 0028–0031 在存在后台/配额/供应商历史时会拒绝破坏性降级，应保留这些约束。

工作流收尾现在只在 prerequisites、migration、workloads 全部为 success 时恢复**已应用候选**的副本；任何失败/取消/跳过/空值均无 kubectl 调用。集群 apply/rollout 自身失败仍使该步骤失败。这个修复不会自动恢复旧数据，也不会把迁移失败转成部署成功。
