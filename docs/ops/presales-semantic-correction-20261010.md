## 1,000字符与12项的依据及调整

Git 追溯到 `b6d1420`（2026-09-19）：`schemas.py` 初始 `TextItem` 设置每项1,000，
`ResponseText.missing_information` 设置最多12。未找到来自真实工作负载的定值证据。
这是应用策略，不是模型token窗口、数据库JSONB或Excel的硬上限。所谓“1,000字”应为
1,000个Unicode码点；本字段是一行答复的待补信息列表，不是全文或整张问卷总容量。

保留单项1,000字符：现有失败没有触及这项限制，它对简短确认事项仍是可用边界，
不把它当作经过用户验证的最优值。将聚合后的12项改为：

- 每项不超过1,000字符，列表文本总量不超过12,000字符（原12×1,000的最大文本预算）。
- 最多156条，来自12个问题片段各12条待补信息，加最多12个未知事项确认动作。
  这是输出结构推导出的容量上限，不是推荐用户填写156条。
- 沿用原有精确去重，保留每条原文和顺序，不再把多个事项以换行合成一条。
- 其他12项边界不变。API、审核、历史读取和前端使用相同规则；数据库无需迁移。
  XLSX仍独立检查整格32,767个UTF-16单元，超长明确报错，不截断。

旧的五份响应离线重放均能形成草稿，其中13和14条保持为13和14条；三个原先成功的
草稿逐字段不变。原始失败报告保持失败，离线验证没有新增模型调用。
旧版程序不能读取新的>12条记录，后续发布必须同步API、Worker与Web；回滚应保留
兼容读取能力，或在明确恢复边界后恢复发布前数据，不能直接假定旧rc50可读新数据。

## 正式修改

- 提示词明确区分买方要求与供应商实际状态。无证明保留未知；明确反证才是不满足；
  同范围未消解冲突需在结构化状态中保留双方证据。
- 保留角色、经验类别、数值、起算点和同时满足关系。同一问题内的多个事项仍只占一个问题编号。
- 修复组装缺陷：每题待补信息与各事项确认动作相加可能超过公开接口的12项上限。
  现仅在必要时把相邻完整字符串以换行分组，保留全部原文和顺序，每项仍不超过1,000字。
  不截断、不推断同义、不改状态；其他字段、引用、问题编号及总答复长度校验继续生效。
- 原始 v21 提示词和历史解析默认行为保留；旧执行策略不能静默变成 v22。
  两个评分器仍将历史失败计为失败。
