# 用户体验与故障恢复验收

2026-09-29，用户要求重新评估性能指标，并将供应商异常作为正常产品场景处理。本次调整验收口径，保留原 160 样本计划及其失败结果，不把旧数据按新门槛重新判为通过。

## 指标为何需要拆分

原“生成受理 p95 ≤250 ms”混淆了点击反馈和经过鉴权、额度预约、持久入队后的服务器确认。现网单次数据库往返约 51 ms，认证会话 GET 已约 239–291 ms。250 ms 适合作为浏览器即时反馈目标，不能直接套用为这个跨数据库事务的服务承诺。

5.69 秒受理仍值得优化。资料版本及最新版本改为合并查询，尝试/复核历史改为批量读取；完整 6 源/12 行响应表采用最多 10 次 SELECT 的工程预算，同时保留初次与返回前的权限检查。这减少数据库往返，不据此宣称线上 p95 已达标。

| 边界 | 新验收口径 | 超出或失败时的体验 |
| --- | --- | --- |
| 点击反馈 | 浏览器提交事件到可见状态 ≤250 ms，单独采样 | 立即禁用重复提交，明确“提交中”，不提前声称已受理 |
| 服务器受理 | 正常负载 p95 ≤2 秒的优化目标；逐请求保留时间 | 15 秒响应截止后恢复实际状态，不把超时当作任务未创建 |
| 后台进度 | 排队、生成、恢复、成功或失败来自服务器；售前活动表每 2.5 秒读取 | 刷新或离页不取消已受理任务，不显示虚构百分比 |
| 模型等待 | 保留现网每条 150 秒执行截止和最多两次派发 | 首次派发最多使用扣除保存预留后剩余时间的一半；给备用路保留机会，重启不延期 |
| 排队 | 与执行耗时单列，保留现网最长 900 秒和准入限制 | 明确排队状态，不将排队+执行宣传为统一 180 秒成功承诺 |
| 临时读取失败 | 有界自动读重试，之后保留手动刷新 | 成功授权读取前隐藏缓存；403/404 拒绝不自动轮询 |
| 最终失败 | 保留要求、资料、失败记录和下一步 | 售前可单独显式重试，三次上限明确，成功行不重做 |
| 额度与费用 | 一个成功任务一次结算，失败释放成功任务额度 | 实际上游派发和未知费用保留，不宣称供应商零成本 |

2 秒是新独立在线复测的优化目标。旧受理 p95 5,688.6 ms、上传 18,699.7 ms、检索 5,558.6 ms 和矩阵未完成仍是现有事实。上传同时记录大小/吞吐、解析同时记录页数/块数；本次单块合成文件不能代表大型文档。

## 已实现的恢复行为

- Agent 创建回执丢失后只自动重放一次相同请求标识；仍未确认时，页面内相同内容的显式重试继续复用它。浏览器存储写入失败不隐藏已受理任务。未确认创建期间保持页面打开；标识不作为跨刷新持久队列。
- Agent JSON 请求有 15 秒响应截止。网络/超时/429/5xx 读取最多重试三次，成功清除旧错误；事件流连续失败最多五次后保留手动刷新。HTML 代理错误保留 HTTP 状态，正文不展示。权限拒绝和不合法成功响应不自动重试。
- 售前后台生成等待 15 秒后只读同一张表确认，不新增生成。临时 GET 错误最多自动再次读取两次。同步旧服务保留独立的 180 秒客户端等待边界。
- 页面区分提交、已受理、后台恢复、终态失败和次数耗尽。供应商异常不伪造答案，不丢失已完成行，也不要求用户反复登录排查。

## 验证边界

真实本地 PostgreSQL/Worker 测试覆盖主模型挂起后备用成功、两路失败、租约恢复、一次结算及未知调用保留。数据库测试覆盖完整 6 源/12 行、条目历史隔离与成员撤销。

售前 Chromium 使用真实本地 API、数据库与后台，覆盖实际离线、受理回执丢失、读取恢复、复核和 CSV，仅替代外部模型。Agent Chromium 覆盖延迟与丢失回执、相同请求标识、审批、产物及桌面/窄屏布局，HTTP 业务边界受控。浏览器单次反馈测量不冒充生产 p95。

线上容量、账单金额、独立业务审核、脱离个人电脑的持续备份及整机 RPO/RTO 各自仍需要实际证据。当前发布状态见[项目最终验收](final-project-acceptance.md)。
