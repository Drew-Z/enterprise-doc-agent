# 单节点告警与恢复验收

首版继续使用现有 4C4G 主机，不新增常驻备用服务器。告警接收邮箱已由经营方提供并保留在本地运维记录。当前已完成现有线上应用数据库与持久对象的本地隔离恢复，以及副本上的历史 API 与受控新业务流程；告警投递、当前主机业务容量和整机故障恢复尚未验收。

## 告警接线

优先使用托管监控服务自带的邮件通知：外部 HTTP 探测和通知都在业务节点之外运行，主机宕机仍能通知；无需在 4C4G 主机上再运行邮件服务器。若已有 SMTP 或邮件 API，可使用该服务的现有受控投递路径。收件邮箱本身不提供发信能力。

接入前只需确定监控服务/发信服务，以及其本地配置或 API 凭据文件路径。凭据不写入 Git、任务正文或命令参数。尚未选择或授权服务时保持未配置，不启动邮件测试。

| 检测项 | 接入位置与初始规则 | 验收证据 |
| --- | --- | --- |
| 公网可用性 | 外部探测 `https://agent.playlab.eu.cc/health/ready`，校验 200 和实际 readiness JSON；建议每分钟一次，连续 3 次失败告警，连续 2 次正常恢复 | 保留外部时间戳、检测结果和故障/恢复通知回执；不能只检查首页 HTML |
| 服务及依赖 | 复用现有 Prometheus API/Worker/Consumer 与 dependency 规则；在选定托管服务配置通知路由或接入受控 Alertmanager | 规则触发、路由匹配、投递回执三者关联 |
| 队列积压 | 在当前容量测试后确定最老等待任务年龄与允许积压量，分别观察在途和死信 | 当前负载样本和审核后的阈值；不凭空给出容量承诺 |
| 备份新鲜度 | 外部心跳记录最近一次完整 DB＋对象快照时间、校验结果；进程失败或心跳缺失触发通知 | 对齐批准的备份周期和 RPO；只有 `pg_dump` 成功不能当完整备份 |
| 主机资源 | 按可观测的磁盘、内存和队列趋势设置通知；使用已有轻量采集或托管探针 | 4C4G 实测资源余量与处理记录 |

表中公网频率是待审核的初始配置。当前没有告警路由和已确认的通知 SLA；Prometheus 规则存在不等于邮件已经送达。正式启用时记录值班人、可响应时间段和超时升级方式，单人运营不能宣称 24×7 独立值班。

外部探测应固定明确的 User-Agent 和 `Accept: application/json`，保存状态码及实际 JSON。2026-09-25 的默认 Python 客户端首次请求出现 HTTP 错误；带上述明确请求头的诊断返回 200 / `ready`，DB、Redis、对象存储均为 `up`。首次错误原因未单独归因，不据此修改线上访问策略；监控服务必须按其真实请求配置完成验收。

投递测试只使用专用测试告警，不中断业务。实际发送前确认具体发送通道、收件人和测试范围；验收至少涵盖一次触发和一次恢复，并由收件人确认收到。不得把本地邮件捕获器或 API 的 2xx 当作真实收件回执。

具体接入模板为 `infra/observability/external-monitor.example.json`，默认未配置、禁止投递；它不是某家服务可直接导入的资源，也不会创建定时任务。经营方确认托管监控账号后，按模板配置外部检测、状态变化通知及既定收件地址。仅支持 HTTP 状态的服务不能证明完整 JSON/时间校验，需记录差异或使用自定义探针。

单次探针可独立运行：

```powershell
& .\.venv\Scripts\python.exe -B -X utf8 scripts/check_external_readiness.py `
  --url https://agent.playlab.eu.cc/health/ready
```

它只执行一次 GET，不发送通知。HTTP 200、JSON 类型、三个必要依赖均 up、ready 和不超过 120 秒的 `checked_at` 才通过；拒绝重定向、登录 HTML、过大正文和无限等待。退出码 0/1/2 分别代表健康、探测失败、配置无效，报告不包含响应正文或异常详情。外部服务负责每分钟调度、连续 3 次失败和 2 次恢复的状态管理。

本机 2026-09-25 的默认直连探针返回 transport_error；使用现有系统 HTTPS 代理的独立对照返回 200/ready。需要使用本机既有代理时显式加 `--use-system-proxy`，报告记录 `network_route`，不改系统代理或禁用 TLS。两个结果分别保留；本机代理成功不证明未来托管监控位置的连通性。

## 不配置备用机时的恢复流程

1. 从业务节点外保留 DB 快照、对象清单/副本、配置与不可变镜像标识。当前 DB/R2 外置降低了应用节点损坏的影响，但同账户误删、凭据丢失和对象删除仍需独立恢复验证。
2. 先在本地 Docker 的全新目标库/对象命名空间验证当前候选，检查原文与产物哈希、DB 引用和租户权限。恢复演练不覆盖正式数据，不回写源对象。
3. 应用节点失效时，使用可用的重装主机或按需新建主机重建运行环境，恢复配置和已核验的数据，再通过登录、上传、检索、人工复核和导出验收后切换入口。此方案不要求常驻备用机，但会有重建停机时间。
4. 独立故障域与 RPO≤300 秒 / RTO≤1800 秒仍须实际演练和审核，当前保持未通过。若经营方后来决定降低服务承诺，应单独评审并修改目标，不能用同机测试自动豁免。

### 本地数据库命令

在仓库根目录使用 PowerShell。`$taskRecoveryRoot` 指向已登记的集中恢复组；继续任务复用该组。下面首先只预览，确认源库是本地测试数据，目标名尚不存在后再执行。

```powershell
$taskRecoveryRoot = 'D:\Agent\codex\backups\tasks\20260924T015840.986Z-commercial-production-readiness'
$drillId = [guid]::NewGuid().ToString('N').Substring(0, 12)
$drillArgs = @(
  '--root', (Get-Location).Path,
  '--compose-file', 'infra/compose/docker-compose.yml',
  '--source-database', 'enterprise_doc',
  '--restore-database', "enterprise_doc_restore_$drillId",
  '--output-dir', (Join-Path $taskRecoveryRoot "artifacts\local-db-$drillId")
)
& .\.venv\Scripts\python.exe -B -X utf8 scripts/local_recovery_drill.py @drillArgs
# 核对后单独执行：
# & .\.venv\Scripts\python.exe -B -X utf8 scripts/local_recovery_drill.py @drillArgs --confirm-local
```

命令使用当前 Compose 中的 PostgreSQL 客户端，不要求 Windows 安装 pg_dump。
已存在的输出目录或恢复库一律拒绝；不会预先删除同名库。恢复失败仍保留备份/日志，默认只清理本次创建的目标。`--keep-restore-database` 用于保留目标检查，后续按报告中的精确名称清理。创建超时、进程被杀或 Docker exec 中断时结果可能不明确，应检查记录，不自动重试或删除未知目标。

私有目录包含 dump、库存、命令和报告；将其哈希登记在同一个恢复组清单，不提交这些私有文件。Windows 下检查目录 ACL；POSIX 的文件 mode 不能替代 Windows ACL。默认报告是该目录的 `report.json`，始终标记 `blocked_external`，不能直接提交为发布通过证据。

### 当前线上数据的只读捕获与本地对象恢复

当前环境使用 PostgreSQL 17.6 / pgvector 0.8.2。数据演练使用应用 `public` schema，排除 Supabase 管理 schema、数据库角色/授权、未完成上传和非持久产物。不要把这项应用数据检查称为完整 Supabase 项目恢复。

1. 在只读 repeatable-read 事务导出 snapshot；表内容摘要和 `pg_dump --snapshot` 必须共用该 snapshot。将 custom archive 经 SSH 直接流入集中本地恢复组，线上不保存主动备份副本。
2. 在全新、独占、无公网端口的 PostgreSQL 17 中恢复。验证 archive SHA、schema 选择和目标空库；只跳过预先存在的 `SCHEMA public` 创建项，不跳过表、数据或约束。本次使用 pgvector 0.8.2 官方镜像固定摘要，恢复目标为 PG 17.10。
3. 对比逐表内容摘要。浮点 JSON 文本可能因 PostgreSQL 小版本而不同：本次 48 张表的原摘要直接一致；`agent_run_evidence.rrf_score` 的 JSON 文本不同，但 IEEE 二进制值与所有其他字段一致。补充检查同时复现原源库 snapshot 的摘要，确认比较的仍是同一批数据。保留首次失败记录，禁止直接忽略该表或四舍五入刷绿。
4. 从恢复库读取 `DocumentVersion` 与持久 `AgentArtifact` 的引用，用 `capture_objects` 只读 GET 源对象。显式给出桶、对象数/字节上限及网络超时；输出目录位于集中恢复组且尚不存在。普通文件与私有 `objects.json` 一起保留，不写源 R2 桶。
5. 在独占 MinIO 中创建空桶，通过 `restore_objects` 恢复原 bucket/key。客户端实际地址必须是回环地址；传入预期清单 SHA，先验证全部本地字节，再排他上传并逐项读回哈希。最后核对全部桶键集合及恢复库的文档/上传/产物引用。
6. 中断时保留首次失败和已校验文件；运营续传必须逐个复核已有文件与同一恢复库记录，只获取缺失项，并单独记录有限请求预算、重试和截止时间。不能把已有目录作为新捕获直接覆盖。
7. 只停止并移除本次独占容器/网络，保留集中快照和私有执行记录。镜像、服务配置、应用启动、租户权限、告警实收与整机恢复另行验收；本地传输/恢复耗时不是生产 RPO/RTO。

2026-09-25 实测：线上仍为 v0.1.44 / 迁移 `20260923_0027`。49 张应用表、79,388 行内容核验通过；642 份文档和 942 份持久 Agent 产物，共 1,584 个对象、1,083,398 字节，全部按 DB 中的 SHA 捕获、恢复到空 MinIO 桶并读回验证。数据库引用集合与对象集合相等，文档与上传会话的对象键无不一致。数据库 archive 为 23,657,879 字节；还原耗时约 2.125 秒，最终本地对象写入/读回约 5.875 秒，均不包含完整准备、传输和应用恢复时间。

首次浮点文本摘要不一致、网络下载失败、900 秒续传时限到期及本机容器准备问题均保留原记录。已校验的 1,278 个文件复用；剩余 306 个经 SSH stdout 只读转发约 54.922 秒完成，无远端文件落盘、无新增重试。整体演练包含准备与排查，不能截取最后这段时间作为 RTO。数据库扩展构建失败后使用官方固定摘要；MinIO 旧标签不存在，改用已运行相同版本镜像的本机 image ID；独占 MinIO 的 internal 网络无法分配发布端口，接入本机 bridge 后仅发布到 `127.0.0.1`。两个本轮临时容器与专用网络已移除，原服务和线上镜像/配置未改。

脱敏机器可读摘要：`.trellis/tasks/09-24-commercial-operations-acceptance/live-local-recovery.json`。完整 DB、文件及失败/续传材料只保留在私有集中恢复组，不上传仓库。上述数据恢复阶段没有启动恢复后的业务应用，没有供应商模型调用、发信、线上迁移或部署。4C4G 的低负载资源基线和公网 readiness 正常不构成业务容量验收。
