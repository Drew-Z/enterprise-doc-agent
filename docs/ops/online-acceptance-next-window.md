## 按顺序完成的运行步骤

1. **生成新的维护执行包。** 复用现有维护守卫和部署流程，以新鲜 rc.1 / 0031 读回生成恢复计划，固定 rc.2 清单、ConfigMap、Secret 版本、Namespace 批准信息及副本。旧维护操作 ID、截止时间、状态库和一次性标记不得复用。先在非停机状态校验模板、权限、镜像可用性及恢复入口，再安排切换。
2. **对齐模型和业务开关。** 提议主路采用本地已经测试过的 `grok-4.7`，备用保留现有 `grok-4.6`；售前从 `fallback` 改为 `primary`。启用后台生成后才允许开启自动切换；按现有单节点方案收敛后台并发。凭据只通过原本地配置和受保护运维入口传递，不写入报告、Git 或命令参数。这些是下一窗口变更提案，本轮没有应用。
3. **先验收完整业务链。** Agent 须经过实际 HTTP、队列/Worker、MCP stdio、检索、持久对象下载与 SHA；售前须核对后台受理、浏览器断网/刷新、同键恢复、复核及 CSV。前一轮本地 Agent 的固定检索/内存对象不能代替该项。冻结具体文档、问题、任务数、全部请求上限和失败停止条件后再执行。
4. **再测当前主机容量。** [容量方案](4c4g-business-capacity-plan.md)的 160 任务仍是待批准工程提案。当前 pilot 额度不足且有历史资料，不是采样器要求的空测试企业。准备独立企业和有限周期，将业务报告、实际 Pod/镜像/配置与遥测阶段绑定，再运行两轮；现有 local-only CLI 不能只换 URL 就指向正式服务。真实模型/向量需独立请求预算；受控供应商需隔离测试配置，不能取消正式环境保护。
5. **按实际账单核对金额。** 将下节应用侧记录与供应商导出逐笔关联，无法匹配、缺少币种或金额均保持未知。没有正式价格时不计算人民币应付金额，不把 quota 当作供应商金额预算。

维护失败时停止新提交并保留在途状态；恢复计划必须覆盖配置和镜像一起回退。0031 保持，不能 downgrade 到 0027。开写后的新账本、原稿、复核及对象保留，不能清库、清队列或换幂等键来重跑失败样本。独立监督器必须在停服前验证。

本轮新增真实模型和向量预算均为零。现网默认 `agent_call_limit=12`、`query_call_limit=6`、解析最多五次尝试且每次向量请求最多三次发送；一个业务任务不能按“一次外部请求”审批。模型修复、主备和 Job 恢复，以及解析拆批/重试，都必须纳入下一批次上限。当前执行包尚缺生产业务执行器与有界外部请求配置，不能提前宣称已可执行全部步骤或要求审批空泛窗口。
