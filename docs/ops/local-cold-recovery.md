# 本地硬件加速冷恢复实测

2026-10-02。第三轮从全新 Ubuntu 磁盘开始，全自动完成历史应用恢复、恢复后新售前业务及测试资源清理，
从故障声明到完成共 **353.051 秒**；选用快照在故障声明时落后 **117.036 秒**，
满足本次本地演练的 RPO 300 秒 / RTO 1800 秒目标。执行期间没有人工修复、控制器接续或重置时钟。
机器记录见[自动恢复核验](../../.trellis/tasks/09-24-commercial-operations-acceptance/automated-recovery-validation.json)。

## 恢复范围

- Windows 原生 QEMU WHPX，2 vCPU / 3 GiB，Ubuntu 24.04；每轮使用官方原始镜像的新 overlay。
- 故障声明后固定当时最新的已验证定时快照，再创建 VM、启动系统、安装 K3s、导入镜像并恢复数据。
- 56 张表 / 82,622 行逐表内容指纹一致；1,668 个对象 / 1,872,148 字节全部读回并核对 SHA-256。
- 使用当前 rc.16 API/Web，真实检查 readiness、33 张历史响应表、CSV 和跨企业拒绝。
- 镜像和安装材料预先准备，准备耗时不计入 RTO。VM 使用本机 SSH 入口及限制网络；应用仅允许同命名空间和 DNS。
- 生产凭据未复制，模型与向量使用受控配置，未调用真实供应商。
- 启动新业务 Worker/Consumer 前，确认恢复库中 jobs、outbox、presales 的历史活动项均为零；不适用于存在历史在途任务的快照。
- 一个新合成企业完成 22 字节 TXT 上传、解析、Core 检索、后台售前生成、两次同键重放、新客户端刷新、技术复核与 CSV。
  本地受控模型 HTTP 请求一次；文档消费恰为 22 字节一次、售前成功额度恰为一次，三态前提及跨企业拒绝通过。
- 43 张涉及企业的历史表内容指纹保持不变，包括 tenant_id 为空的原有记录；七项验证资源清理且原 API 配置恢复。

本结果证明当前无历史活动任务的快照与预备材料能够全自动恢复到本地完整 VM，读取历史业务并运行新的售前业务。
它不证明历史在途任务恢复、新 Agent/MCP 全链路、真实供应商、云主机申请、公网切换、生产 OAuth 或值班响应。
个人电脑离线时的备份连续性也需要独立完成，五项商业放行门槛仍未全部关闭。

## 保留的失败与修复

| 问题 | 实际处理与验证 |
| --- | --- |
| WHPX 默认中断控制器导致无法启动 | 使用 `whpx,kernel-irqchip=off`；独立空白 Ubuntu 启动约 56.5 秒 |
| Windows `ssh-keyscan` 不支持协商出的 KEX 方法 | 从已确认归属的 VM 串口取得主机公钥并验证指纹，后续 SSH 严格校验；不关闭主机校验 |
| 卷辅助镜像不在运行中镜像清单 | 将精确 BusyBox 1.37.0 镜像纳入离线材料；实际 PVC Bound 后才继续 |
| containerd 有镜像内容，但缺少 CRI 要求的别名 | 对照源/别名的同一摘要，只补齐缺失引用，再验证容器启动 |
| `kubectl exec` 归档流超时或截断 | 24,210,919 字节归档曾只收到 32,768 字节；哈希检查拒绝继续。改为 SSH 文件传输及已核验归属的容器文件复制，逐处核对 SHA；归档清单在容器内产生，避免未消费的 stdin |
| 恢复后业务夹具缺字段或不符正文契约 | 补齐合成额度时间戳；受控模型输出遵守现有中文正文契约，不放宽生产校验 |
| 排除合成企业时遗漏原有空企业行 | 使用 `tenant_id IS NULL OR tenant_id NOT IN (...)`，保留原 browser_sessions 一行和 browser_session_events 四行；不删除历史数据使比较通过 |

第一轮在 1800 秒截止时未完成，随后诊断恢复到应用共 2681.426 秒，仍判为 RTO 失败。
第二轮初次控制器与一次传输接续也有失败记录；最终同一时钟内完成不删除这些失败。
第二轮历史应用最终恢复 883.364 秒、RPO 189.325 秒，属于包含人工修复的通过结果；其后新业务四次局部验证的前三次失败也独立保留。
第三轮将已验证修复整合到冻结执行器，从新磁盘自动完成，不复用第二轮恢复后的磁盘。
此前软件模拟 VM 的 9899.813 秒数据至应用结果同样保留。
