# 本地硬件加速冷恢复实测

2026-10-02。第二轮从全新 Ubuntu 磁盘开始，在 **883.364 秒**内完成历史应用恢复；
选用快照在故障声明时落后 **189.325 秒**，满足本次本地演练的 RPO 300 秒 / RTO 1800 秒目标。
途中修复和控制器接续时间全部计入，没有重置时钟或更换快照。
机器记录见[恢复核验](../../.trellis/tasks/09-24-commercial-operations-acceptance/hardware-recovery-validation.json)。

## 恢复范围

- Windows 原生 QEMU WHPX，2 vCPU / 3 GiB，Ubuntu 24.04；每轮使用官方原始镜像的新 overlay。
- 故障声明后固定当时最新的已验证定时快照，再创建 VM、启动系统、安装 K3s、导入镜像并恢复数据。
- 56 张表 / 82,622 行逐表内容指纹一致；1,668 个对象 / 1,872,148 字节全部读回并核对 SHA-256。
- 使用当前 rc.16 API/Web，真实检查 readiness、33 张历史响应表、CSV 和跨企业拒绝。
- 镜像和安装材料预先准备，准备耗时不计入 RTO。VM 使用本机 SSH 入口及限制网络；应用仅允许同命名空间和 DNS。
- 生产凭据未复制，模型与向量使用受控配置，历史后台队列保持暂停，未调用真实供应商。

本结果证明当前快照与预备材料能够恢复到本地完整 VM 并读取历史业务。
它不证明云主机申请、公网切换、生产 OAuth、恢复后的新业务生成、无人值守恢复或值班响应。
个人电脑离线时的备份连续性也需要独立完成，五项商业放行门槛仍未全部关闭。

## 保留的失败与修复

| 问题 | 实际处理与验证 |
| --- | --- |
| WHPX 默认中断控制器导致无法启动 | 使用 `whpx,kernel-irqchip=off`；独立空白 Ubuntu 启动约 56.5 秒 |
| Windows `ssh-keyscan` 不支持协商出的 KEX 方法 | 从已确认归属的 VM 串口取得主机公钥并验证指纹，后续 SSH 严格校验；不关闭主机校验 |
| 卷辅助镜像不在运行中镜像清单 | 将精确 BusyBox 1.37.0 镜像纳入离线材料；实际 PVC Bound 后才继续 |
| containerd 有镜像内容，但缺少 CRI 要求的别名 | 对照源/别名的同一摘要，只补齐缺失引用，再验证容器启动 |
| `kubectl exec` 归档流超时或截断 | 24,210,919 字节归档曾只收到 32,768 字节；哈希检查拒绝继续。改为 SSH 文件传输及已核验归属的容器文件复制，逐处核对 SHA；归档清单在容器内产生，避免未消费的 stdin |

第一轮在 1800 秒截止时未完成，随后诊断恢复到应用共 2681.426 秒，仍判为 RTO 失败。
第二轮初次控制器与一次传输接续也有失败记录；最终同一时钟内完成不删除这些失败。
此前软件模拟 VM 的 9899.813 秒数据至应用结果同样保留。
