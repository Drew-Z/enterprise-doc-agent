# rc.16 数据库连接延迟诊断

2026-10-02。当前应用版本为 `v0.1.45-rc.16`，源码
`63de37c080cd83a02682ad1d2dd30c217a6aecd7`。

已复现应用主机到数据库连接上的 TCP 重传，尚未定位具体丢包或延迟确认的物理节点，
也没有验证有效的长期修复。该发现解释了部分等待，不能据此把全部业务延迟归因于网络，
或把此前未达标的容量结果改为通过。

机器记录见 [rc.16 网络诊断](../../.trellis/tasks/09-24-commercial-operations-acceptance/rc16-network-diagnosis.json)。
全部脚本、原始时钟、TCP 计数、失败尝试及来源哈希保存在原集中恢复组的
`rc16-release-evidence`，没有修改线上数据库配置、表结构或主机网络参数。

## 1. 根因类别

**E：隐含假设。** SQL 次数减少是可验证的代码改善，但不保证远端数据库调用耗时按比例下降。
原先仅观察查询次数和整条业务耗时，不能区分 SQL 执行、连接等待和 TCP 重传。
现在已有独立于业务表的传输证据；物理故障来源仍未知。

## 2. 为什么已有优化没有达到目标

rc.16 四个新任务全部成功，上传 p95 为 10,779.884 ms，受理为 4,714.538 ms，
检索为 4,482.413 ms，仍未满足各自的 5,000 / 2,000 / 2,000 ms 目标。
该批模型 4 次、向量 12 次，没有触发真实主备切换。

随后用一个新的 678 字节 PDF 在同一 API Pod 的独立诊断进程中调用已部署 ASGI 路由，
保持实际数据库、对象存储、鉴权和上传校验。四次 HTTP 操作耗时分别为：

| 操作 | 耗时 ms |
| --- | ---: |
| 创建上传会话 | 3,420.785 |
| 分片签名 | 1,076.999 |
| 上传分片 | 1,591.486 |
| 完成上传 | 6,036.455 |

完成上传包含对象列表、完成合并、HEAD 和内容读取，以及多个短数据库事务。
有些 SQL 约 50 ms，另一些约 300 ms。该窗口 CPU 限流时间为零。
上传及后台解析成功，只新增 1 次向量调用、0 次模型调用；这是单独冻结的诊断预算。
独立 ASGI 进程的时钟不冒充正在提供服务的进程或公网浏览器时钟。

162 个有界常量查询样本进一步区分了假设：

| 对照 | 观察 | 结论边界 |
| --- | --- | --- |
| `SELECT 1`，仅改变注释长度 | 小请求通常约 50 ms；8 KiB 请求曾达 1.1–1.3 秒 | 不读取业务表也会变慢，不能只寻找业务索引问题 |
| TCP_INFO 前后计数 | 慢样本出现新增重传；重传超时约 250 ms；TCP_NODELAY 已开启 | 重传产生实质等待，尚不能定位丢包或延迟确认的节点 |
| 主机与 Pod 网络 | 两者均复现重传 | 不能将故障仅归于 Kubernetes 网络 |
| 5432 / 6543，关闭自动 prepared statements 的对照 | 一次 24 样本窗口均约 53 ms、无重传；之后地址固定对照仍复现 | 短暂正常不是端口或 prepared statements 修复的证明 |
| 三个当时解析的地址，分别使用阈值 5 / None | 各地址均出现大请求重传 | 没有验证可长期固定的健康地址，不固定云服务 IP |
| 每连接 MSS 1000，对照默认值 | 实际 MSS 降低，仍有重传 | 不据此修改主机 MTU |
| 独立本地 TLS 透传，1 KiB 分段、5 / 10 ms 间隔 | 部分延迟下降，但仍重传 | 不能作为已验证的上线方案；透传监听已关闭 |
| 主机发送队列 | 所查队列丢包计数为零；实际经 eth0 出站 | 未发现该层本地队列丢包，不证明整条路径无丢包 |
| 同项目直连地址 | 仅解析 IPv6，当前目标连接返回网络不可达 | 现有网络不支持该直接替代路径，未发送数据库凭据 |

主机对照执行器前三次因 namespace 根目录/工作目录参数失败，原回执保留；
使用实际验证过的解释器命令后成功。直连诊断首次被旧项目标识断言拒绝，
后续从已批准的实际 DSN 派生同项目地址；首次没有执行 DNS 或认证。

## 4. 后续处置

需要修复或替换当前不稳定的数据库连接路径，并用上述常量查询和 TCP 计数验证。
可由现有主机/网络供应商排查，也可在用户以后提供可用资源时比较其他受控主机、网络或数据库接入方式。
本记录可以作为故障复现材料；助手尚未向供应商发送消息，也没有申请额外云资源。

路由变更提案必须给出具体目标、TLS/权限约束、连接上限、恢复点和回退执行方式。
优先完成多连接的稳定传输对照，再冻结新的业务与供应商预算。
原四任务、失败的 160 任务分母和费用记录不能复用或重写。
此时仍可继续改进已证实的产品问题，但不能声称现有验收目标已经通过。

## 6. 后续替代路径实测

继续完成五项验收时，新增独立诊断；没有改变应用镜像、数据库地址、主机路由或生产连接池。
机器结果见[替代路径核验](../../.trellis/tasks/09-24-commercial-operations-acceptance/network-alternative-validation.json)。

- 单个诊断连接的73个TCP包头与8个常量查询显示：大请求发出后，对端ACK/SACK留下序号缺口，
  补发后才推进；两个8KiB查询分别约382和688ms。抓包内核丢包计数为零，仍不能定位物理丢包节点。
- 64个常量查询比较默认发送与每连接64/32/16KiB/s内核限速。设置读回确实生效，
  每组仍有重传；最低速率还出现约1.62秒样本。因此不修改生产限速或拥塞控制。
- 在现有Cloudflare账户建立了限定目标、鉴权、绝对过期和流量上限的临时WebSocket/TCP转接。
  原数据库TLS从客户端贯穿转接，使用Supabase官方CA和原主机名进行`verify-full`验证，
  Worker不解密SQL或凭据。`workers.dev`不可达的首次失败保留；改用独立自定义域名后实测成功。
- 自定义域名对照共32个常量查询、4个独立连接。16个直连样本为47.309–50.121ms；
  16个转接样本为356.761–563.586ms。转接没有达到降低短查询延迟的目的，不接入生产。
  两组所测客户端TCP段均未新增重传，但不能据此认定原路径已修好，或证明Cloudflare至数据库段无重传。

系统CA不能验证该Supabase证书链。CA下载位置由Supabase官方Studio源码确认，证书经HTTPS取得；
诊断用内存文件描述符提供给libpq，结束后关闭，没有降低TLS校验或修改系统信任库。
这只是验证过的连接参数，不代表线上已启用`verify-full`。

临时Worker、自定义域名及其DNS记录均已读回确认移除。第二版执行器在清理时误将成功的空HTTP响应
作为JSON解析，原异常保留；先检查实际资源状态，再仅移除剩余的本轮Worker。该版没有可用的查询回执，
不计为成功试验。后续执行器兼容空成功响应，并完成端到端验证与清理。

本阶段应用模型/向量调用及业务写入为零。搜索工具连通性自检另有一次聊天请求，不并入应用容量账本，
金额未知。诊断脚本、失败回执与证书来源继续保存在原恢复组的`rc16-release-evidence`。
性能与两轮容量仍开放；当前证据不支持把这条转接路线发布为性能修复。

## 7. 实际预编译复用对照

后续 144 个常量查询在六个独立会话中比较阈值 None / 0 / 5；每条相同语句执行八次，
通过 `pg_prepared_statements` 确认 0 和 5 两组各有三条常量语句真正进入预编译缓存。
原地址对照每条只执行两次，不能据其阈值 5 设置推断已经测过预编译复用。

| 阈值 | 8 KiB 首次执行中位数，2 样本 | 第 7–8 次执行中位数，4 样本 | 后四样本新增重传 |
| --- | ---: | ---: | ---: |
| None | 725.127 ms | 74.566 ms | 3 |
| 0 | 636.541 ms | 50.872 ms | 0 |
| 5 | 1557.326 ms | 48.618 ms | 0 |

预编译复用减少重复发送长 SQL 的等待，但首次准备仍复现重传，各组处于不同短窗口。
现网默认阈值已经为 5；这个小样本不能证明改成 0 能使新业务受理达标，也未验证连接回收、
真实参数长度或大结果集。没有修改生产配置或宣称两轮容量通过。
只读查询及本地冷恢复结果一起记录在[新增核验](../../.trellis/tasks/09-24-commercial-operations-acceptance/hardware-recovery-validation.json)。
