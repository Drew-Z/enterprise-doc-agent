# 问卷系统成熟方案、反复错误归因与调整建议

研究日期：2026-10-11（Asia/Shanghai）。代码基线：
`b4f1e6a88fccc875259c8a0fd5471b1740764788`。

结论：市面上已有可采购的问卷/RFP 产品，也有可以复用的检索与评估组件。
本项目不需要继续从零探索整个问题。当前应调整“遇到一题失败就追加提示词”的推进方式，
先建立成熟方案对标，把已确认的检索缺陷、业务语义缺陷和协议问题分开处理。
官方产品功能说明可以证明已有实现路线，不能证明某个产品已经通过本项目的案例。

## 1. 已核实的成熟产品与组件

这不等于证明全市场没有这种产品；它意味着不能以宣传语代替本项目的实测。
本轮没有采购、注册账号、联系销售、上传项目数据、安装框架或下载模型权重。

## 2. 本项目已经能够确认的原因

### 2.1 证据存在，但没有送到模型：检索与证据选择问题

历史密码题原文明确有 minimum 8 / maximum 128，关键段在 offset1080，旧稿引用的是
offset0、2160。ISMS 文档也有明确的范围限制，旧自动生成输入没有提供该关键段。
这类错误不能要求生成模型仅靠提示词补救。

代码位置：`generation.py:485-508` 每来源至多两段，每段前1800字符；
`retrieval_selection.py:24-40` 的 v25 选择只看已召回前10候选，按新增词覆盖选择第二段。
它明确没有语义分类。词语多样性不等于“覆盖所有回答必需的事实”。
`documents/retrieval_service.py:196-269` 已经有关键词全文检索、向量检索和 RRF；
所以本项目并非“没有 RAG”，也无需重新建设基础向量库。

v25 的受控向量 PostgreSQL 测试证明特定证据可以被送达。随后的四题真实生成使用人工选定摘录，
范围与密码数值已有改善，但这不能证明真实 embedding/rank 链路已修复，也不能单独归因于新提示词。

### 2.2 “问政策是什么”与“判断业务前提是否满足”共用协议

`schemas.py:45-48` 的题目输入只有 key、text、source_location，没有题型执行约束。
`question_assessment.py:179-186` 所有题共用 rules、assessments、responses、status、conclusion。
规则数组可以为空，但没有独立模式阻止普通事实问答输出业务前提。

四题真实回归中的密码答案已经正确说出8/128，却把“GitLab 默认执行密码要求”同时写进
rules 并标为 met，随后被渲染为“核验事项”。它没有新要求客户做一个动作，
但把政策事实错分成业务前提，说明剩下的问题不是缺少密码材料。

更早的 v24 还按标点拆题，将 PCI DSS 背景示例和 Yes/No 选项变成需要分别回答的片段。
v25 保留整行修正了这个具体机制；它并未同时解决所有事实/义务分类问题。

### 2.3 校验了真实引用，未验证引用是否支持业务解释

`assessment_selection.py:133-147` 的 resolver 明确说明：

> Project declared roles and actions; never infer whether a span entails a claim.

它检查规则覆盖、引用、文本覆盖和字段组合，再在179-205行投射模型声明的规则与状态。
这能有效拦住不存在的引用、错位编号及不合法组合，却不能证明：

- `requiredBy` 指向的原文真的使某事项成为当前业务的必要条件；
- 一段“未登记结果”的文字能否证明“事情没完成”；
- 正文、结论和下一步是否表达了同一个判断；
- “集中管理”是否被擅自收窄为“必须使用单一平台”。

真正的缺口是缺少这些语义关系的独立约束或复核。增加一个必填的来源ID字段本身不能填上缺口。
已有人工复核和导出流程仍有价值，不能说项目完全没有审核机制。

### 2.4 格式复杂度不是已证实的唯一原因

[最小协议实验](D:/workspace4Cursor/enterprise-doc-agent/docs/ops/presales-minimal-contract-observation-20261010.md)
将输出简化为一个答案字段，仍出现“没记录→没完成”和无依据的培训证书义务。
这证明这类错误不以嵌套 schema 为必要条件；但该样本与复杂协议样本不同，不能当作严格消融实验。

[同样本 low/medium 对照](D:/workspace4Cursor/enterprise-doc-agent/docs/ops/presales-reasoning-comparison-20261010.md)
只改变请求的 reasoning_effort，两次均未通过语义门槛。
这是当时 grok 路由的一组观察，不能推广成当前 gpt 路由或所有模型的能力结论。

本轮取证发现当前 v25 system 文本8638字符，另有 response_format schema5589字符，
三道 GitLab 题提供30–55个 span；这种输入有优化空间。不过 CQU06 仍能正确处理12项义务，
所以“协议负担导致所有错误”也未获证明。具体模型能力、协议负担各占多少，需要固定输入的对照。

### 2.5 迭代方法需要改变

此前机械修复、权限/账本测试及失败记录保留是必要工作；问题在于后续推进过于围绕单个失败案例
加提示词、改协议。单元测试用受控模型输出验证服务行为，本来就不能验证真实模型理解。
看过并用于调整方案的题，也不能重新算作未见过的验收集。

最新四题应分级处理：范围题和复杂售后题通过；密码题是结构化语义缺陷；设备题的正文已允许
“其他集中式机制”，只是结论仍偏向统一平台/中央控制台，属于措辞收敛，不能和伪造业务义务等量齐观。

## 3. 推荐路线：复用通用能力，保留项目边界

如果目标仅是企业内部更快完成问卷，应优先让 Vanta、Conveyor、Loopio 用同一组公开案例做对标，
再比较审核用时、引用准确性、中文表现、表格保真、接口、许可与总成本。
目前没有这些 SaaS 的账号试用回执，因此只列候选，不宣布采购胜者。

对于本项目继续形成自有产品的目标，推荐先复用 Haystack 的检索组件和 Ragas 的评估组件，
保留现有 PostgreSQL、权限、配额、幂等、失败证据、复核及 Excel 导出。
不要同时换数据库、编排框架、全部提示词和主备模型；那样无法判断改善来自哪里。
本轮没有完成依赖版本、许可、模型权重许可或资源适配验证，接入前须做最小适配检查。
现有4核4GB环境尤其不能默认适合部署大型本地 reranker。

### A. 先区分回答任务，限制模型能做什么

普通政策/事实题走“回答＋引用＋真正缺口”的路径，服务端不接受业务前提输出。
只有明确涉及条件满足、供应商合规或能否启用的题才进入条件评估；混合题分别处理相关部分。
题型依据可审计的题目上下文/导入元数据或经过评估的分类器，低置信度留给复核，
不能只看到原文有“必须”就进入业务前提路径。分类器本身也要测，不能把错误搬到上游。

条件评估应保留义务主体、适用对象、触发条件、时间和例外。
事实抽取与条件必要性都须有依据；归一化以后再使用明确的状态规则。
例如“培训完成、证书未附”只说明培训完成，不能自动派生证书提交义务；
“验收结果未记录”保留未知，不能推成未验收或已经通过。
规则引擎只能执行已明确的规则，不能替代原文理解。当前状态有限，不建议先引入重型规则引擎。

这是执行路径和责任划分的调整，不是再给同一个万能 prompt 添加几个字段。

### B. 优先复用已审核答案，生成只覆盖真正的新问题

现有生成链路主要检索上传文档。可以将已复核答案连同供应商、产品、版本、适用范围、时间、
原始引用和批准状态形成可复用条目；先匹配同一范围的已批准内容，再考虑生成。
这是 Vanta/Loopio 等成熟产品已经公开采用的模式，不必重新发明。

该机制不能把上一订单的“已完成”带到新订单，也不能把 GitLab 演示材料当作本项目自己的承诺。
当前 Codex 复核过的公开案例仅是测试资料，不能静默升级为企业正式批准的答案库。

### C. 修证据供给：重排与上下文恢复，分别评估

在已授权候选上比较现有 v25 选择与现成 cross-encoder 重排，必要时取同一来源的邻近窗口或父段。
保留租户、文档版本、generation、原文偏移和可引用范围，不因组件接入丢掉授权校验。
完整条款及其例外应能共同进入上下文。窗口扩大也会引入无关内容，因此总字符/成本上限必须显式设定。

第一步先在相同候选和相同证据预算下比较选择器；随后单独评估上下文恢复预算。
分别记录关键事实在全库、前10候选、最终输入中的位置。
前10里没有关键段时，不能指望 reranker 找回来，需要回到召回/切分层解决。

### D. 用现成评估组件补齐语义验收，不以模型自评分放行

将评估拆成三层：关键证据有没有找全、答案中的每个重要主张是否有依据、问题与义务有没有漏答。
Ragas 可提供这几类指标的实现；业务专用标准还需包括缺失/失败区分、跨范围复用、数值边界、
新增义务、正文/结论/下一步一致性。不能仅以平均分掩盖一项严重错误。

先离线运行辅助评估，人工核对重要分歧并校准阈值；不要默认给线上每题再加一次模型调用。
后续如需在线语义检查，必须单独说明调用预算、延迟及误判处置。
严谨引用、人工复核和失败保留继续保留；自动检查只降低风险，不承诺消除所有理解错误。

## 4. 有限验证计划与停止条件

| 阶段 | 固定内容与单一变量 | 交付物 / 通过条件 |
| --- | --- | --- |
| 诊断基准 | 保留已知失败；逐题冻结必要事实、原文位置、合法答案边界、禁止新增的义务 | 区分检索缺失、解释错误、协议拒绝、措辞问题。没有参考的项不报告准确率。 |
| 检索组件对照 | 相同文档、查询、embedding、候选和预算；一次只换选择/重排；上下文窗口另作对照 | 比较关键事实到达率、引用偏移、权限、延迟及资源；不先调用生成模型来掩盖召回差异。 |
| 生成对照 | 提供相同正确证据，固定模型/渠道；比较现协议与按题型受限的路径；模型对照另作一组 | 保留首结果；评估事实、条件类型、状态、行动和完整性。不通过就报告失败，不原题反复抽到通过。 |
| 扩展验收 | 使用尚未用于方案调整的第二供应商材料；提前冻结范围、参考、调用上限和失败标准 | 同时看正确率与拒答率、实质修改量、审核时间、费用/未知用量和导出保真。没有参与者时只能做开发验证。 |

有限验收集内，跨租户/版本引用、虚构事实、无依据新增义务、把未知变成通过/失败应作为阻断项；
“这一批未出现”只表示该批通过，不是总体零错误保证。耗时和修改量若未改善，也不能宣布方案优于现状。
任何新的真实模型对照都先另行冻结有限预算。本轮没有执行这些新实验。

主备切换属于可用性控制，和上述回答质量是不同问题。重试同一错误路径或换备用模型不能证明语义正确。
已准备的主备策略方案保留，但不作为此次质量整改的第一优先级；不顺带更改线上配置。
