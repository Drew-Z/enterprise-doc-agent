## 1. 产品决定与需要验证的假设

**首版定位：面向中小 B2B 软件与 SaaS 供应商的技术、安全问卷响应工作台。**

客户提供买方问卷和本企业资料，系统复用有效的已批准答案，检索必要证据，生成有出处的草稿和明确的缺口，经人工审核后回填原工作簿，并把可复用内容沉淀到企业答案库。

### 1.1 首批目标客户

| 项目 | 首轮选择 / 假设 |
| --- | --- |
| 组织 | 向企业销售软件或 SaaS，反复收到技术、安全或供应商尽调问卷的小团队；按工作频率筛选，不先按公司人数筛选 |
| 日常使用者 | 售前工程师、解决方案工程师、兼任安全答卷的技术负责人 |
| 审核与付款决策 | 售前/技术负责人；具体职责在试用开户时明确 |
| 需求信号 | 建议优先寻找每月至少两份问卷、答案分散在文档和旧表格、目前靠复制粘贴和反复找人确认的团队；这是招募假设，尚无市场验证 |
| 首版文件 | XLSX 为主，CSV 为补充；优先中文界面，回答语言跟随问卷；双语正确性单列评估 |
| 首轮规模 | 先验证每份 20–60 题的小中型问卷。现有 XLSX 代码上限 120 行、2 MiB、最多 6 个资料来源，生成批次入口最多 12 行；这些是约束，不是已经验证的并发容量 |
| 获客方式 | 受邀试点、经营者协助首次建库、有限期限与额度；已有公网演示可用于展示公开材料 |

首版承诺是帮助团队更快形成**可复核、可追溯、可交付**的答卷。不会把公开供应商政策自动解释为客户自己的配置、执行记录或合规证明。

选择该方向的依据：现有导入、文档检索、人审和导出最接近这项工作；重复问卷能够验证答案复用的收益；专业竞品公开的答案库与审核流程说明已有产品模式可借鉴。中文、轻量部署、价格和响应质量上的竞争优势均尚未证实。

### 1.2 首版范围与后续范围

**首版必须形成完整闭环：** 企业准入与范围确认 → 资料与问卷导入 → 有效答案匹配 → 检索与草稿 → 缺口/人工接管 → 复核 → 原表导出 → 答案入库 → 后续问卷复用与过期复核。

后续再考虑：复杂招投标全文写作、法务自动承诺、第三方门户自动填报、CRM/网盘连接器、通用 Agent 市场、多 Agent 协作、公开自助订阅、私有部署产品线和高可用架构。客户的真实需求可以改变顺序，但这些功能不作为当前首版的默认前置。

既有 4C4G、不新增备用服务器的限制保持。已延期的持续备份/进一步灾备仍标为未验收，不由本计划静默撤销或改成通过。真实敏感资料接入及商业合同范围要与实际数据保护能力一致；到该阶段再明确需要补齐的能力或可接受的数据范围。

| 证据与语义候选 | 已有题型分流、上下文窗口和重排候选/局部观察 | 关键范围/数字遗漏、条件类型混用仍存在；局部通过不等于全部候选已上线或有效 |
| 答案复用与知识维护 | 已有原稿/复核历史、固定资料版本与 stale-source 保护 | 本轮定向检索未见完整的可批准答案库及其来源变化影响管理；历史复核不是完整答案库 |
| Agent 编排 | 已有固定 LangGraph、checkpoint、内部 MCP 与人工审批 | 复用现有基础；模型自主补检索只在有收益时加入，不因名称而迁移框架 |
| 客户与经营 | 第二供应商试用包已准备；目前参与者为 0 | 没有独立 UAT、人工节省时间、付费意愿或收入证据 |
| 状态维护 | README 的 rc.44、旧商业计划的 rc.47 与后续 rc.51 记录并存 | 首个工作包统一当前入口和版本绑定，历史记录继续保留 |

最紧要的缺口依次是：任务失败的可控处理、回答所需证据供给、事实与条件的正确解释、可复用答案资产，以及独立使用反馈。测试数量、框架数量和研究报告数量都不能代替这些结果。

## 3. 产品闭环与验收行为

| 编号 | 用户可观察行为 | 验收例子 |
| --- | --- | --- |
| V1 范围与导入 | 指定产品、版本、部署形态及所回答的企业；预览工作表和列映射 | 不支持的工作簿在导入前给出原因；支持模板题目无丢失，答案写入指定单元格 |
| V2 可信答案复用 | 优先建议同租户、同适用范围、仍有效的已批准条目 | 上一客户的部署状态不能移用；近似匹配显示差异；失效条目不能自动复用 |
| V3 新问题取证 | 找到关键事实、限制与例外，区分政策问答和执行状态核验 | 原文有密码长度时回答保留数值；政策说明不自动证明本企业已经配置 |
| V4 缺口和失败 | 区分资料不足、范围不适用、模型失败与等待处理 | 单题模型失败后，其余已完成行可保存和导出；可人工填写，原失败仍可追溯 |
| V5 审核与交付 | 显示答案、证据、必要补料，修改有作者与历史 | 未复核内容只导出为草稿；已复核导出保留必要限定，非答复单元格保持 |
| V6 知识积累 | 将选定的复核结果明确批准入库，设置负责人和复核时间 | 原资料变更/撤销时标记依赖条目待复核；旧交付记录保持历史身份，不悄悄重写 |
| V7 运营与退出 | 开户、有限额度、支持、到期、导出和退出有明确流程 | 失败和重试不重复业务结算；调用成本与成功任务分开记录；退出操作可核验 |

UI 主流程围绕问卷、答案、证据和复核展开。模型渠道、协议版本、底层重试等保留在运行记录/诊断界面，不要求客户理解它们才能完成答卷。

### 3.1 最小答案库设计

条目至少包含：企业、问题/答案、产品与部署范围、来源版本/原文引用、答案类型（通用政策或特定执行事实）、批准状态、负责人、批准时间、下次复核时间和撤销原因。

复核保存与批准复用是两个动作。公开测试材料及 Codex 辅助复核默认保留测试身份，不能进入真实企业的正式答案库。初版先做人工选择入库和建议匹配；不引入自动跨企业学习，也不把相似度当成正确概率。

资料的技术版本变化与业务有效期是两个信号。现有 stale-source 保护继续使用；答案库增加依赖关系和有效期状态。首次实现可以由重新上传/管理员标记触发，不先建设外部连接器和全网抓取。

## 4. 技术取舍与复用决定

| 领域 | 本计划决定 | 通过标准 / 退出条件 |
| --- | --- | --- |
| 模型 | 首版推荐固定当前 GPT 主线路与版本化契约；取消未经同标准验证的自动跨模型交付 | 这是待实施策略。不能仅凭模型名称断言第二渠道等价 |
| 重试 | 单题最多两次计入账本的派发，符合分类的短暂故障可用第二槽重试同主路；用尽后可见失败与人工接管 | 未知发送状态、半截流和超时不自动当作未发送；完整输出的语义/引用错误不靠重复抽样放行 |
| 通用模型接入 | 给 LiteLLM SDK 一个最多两天的兼容性验证窗口；保留薄业务适配层 | 检查现有渠道/流式/结构输出、异常分类、usage 与请求数。关闭 SDK/代理隐式重试，保留一处重试决策；无明确收益就保留现有薄适配，不继续扩建网关 |
| Agent 运行时 | 保留 Python / LangGraph；本阶段不全量迁移 Pi | 框架替换只有在具体维护成本或质量对照支持时才重新评估 |
| 检索 | 继续 PostgreSQL/pgvector 与既有 Haystack，先评估关键证据到达，再选邻近窗口/重排 | 前候选中没有证据时先修召回；权限、版本、原文偏移和上下文上限必须保留；不在 4C4G 上默认部署大型重排模型 |
| 回答方式 | 分离事实问答、条件/执行状态核验及混合题，复用已做候选 | 简单题不强制生成前提清单；题型不确定可人工纠正。逐字引用合法和语义支持分别评估 |
| 答案库 | 借鉴 QResponder、TrustReply 和商业竞品的已批准内容优先/复核回填模式 | 引入代码前固定提交和许可证；不直接复制未经评估的阈值或“批准后永远有效”的假设 |
| 评估 | 先用现有评测入口和业务断言；Ragas 可作为离线辅助，人工核对分歧 | 不把模型自评分作为放行；DSPy 只在已有冻结数据与预算后作为可选优化，不先引入第二套平台 |

有限自主补检索属于可选能力切片：固定取证仍不足时，让模型在已授权的 `search_documents`、`read_source` 和 `find_approved_answer` 等业务工具中选择必要操作，随后作答或留下缺口。工具名为设计接口，当前不宣称已实现。

先验证最多一次模型发起的补检索与一次最终作答。若合计用掉两次模型派发，就没有额外重试槽；工具调用、embedding 与模型派发分别计量。任何扩大派发上限的设计要单独更新持久策略和预算。它默认不成为首版阻塞项，只有独立集上的质量/修改量收益覆盖成本和延迟才启用。

模型重试、题型分流、检索优化和答案复用分别评估。每次对照只改变一类因素，避免同时更换模型、协议、检索、资料和框架后无法归因。

## 5. 质量与泛化验证计划

### 5.1 数据划分

1. 已看过且据此改过实现的 SWU/GitLab 题及全部历史失败进入开发/回归集，持续保留。
2. 现有 GitHub 第二供应商六题包可以先做迁移诊断；六题不足以作为商业质量结论。若其内容已用于调参，则归入验证/开发，不再称独立留出。
3. 首轮规划约 75 题：30 开发、15 验证、30 独立测试。按供应商/产品/文档版本分组，至少覆盖三个独立资料包；具体数量在样本盘点后冻结。这是计划规模，尚未采集或运行完毕。
4. 独立测试在候选冻结后才评分；参考答案不进入模型上下文。发现测试失败后可修复，但该批转入回归，新的泛化结论需要另补未用于调整的材料。
5. 同时包含有充分证据、明确反证、缺证据、例外条件、版本冲突、数值边界、执行状态和不适用范围。完整政策与真实执行证据必须分开标注。
6. 增加换数字、换版本、删除证据、插入矛盾材料、换布局与问法的变形测试；合成内容明确标注。增加文档中的恶意指令用例，检索内容不得获得工具权限或改变审核规则。

公开材料用来开发和检验迁移能力；真实授权客户资料用来验证实际任务收益。多收公开文件不能替代真实使用者，也不能把公开资料缺少企业内部事实误当成模型能力缺陷。

### 5.2 分层指标与首轮建议门槛

以下是候选进入受邀试点前的建议验收目标，非当前已达到数值，也不是统计总体保证。各批执行前固定分母、严重性规则、参考、预算及版本；不得看完结果后改门槛。

严重错误至少包括越权取证、虚构关键事实、跨产品/版本承诺、把未知执行状态改成已满足/未满足，以及无依据增加合同义务。质量统计保留冻结题集的完整分母，失败和未运行单列，不能只对成功草稿报告总体质量。参考结论须对应原文，自动评分与人工语义复核分开；助手复核只算开发验证，真实领域/使用者验收由实际参与人完成。

| 层次 | 指标和首轮目标 | 计分边界 |
| --- | --- | --- |
| 来源与权限 | 测试内跨租户/撤销权限泄露为 0；引用位置与版本校验全部通过 | 自动检查失败直接阻断；不能用平均分抵消 |
| 检索 | 标注的关键证据最终到达率目标 ≥90% | 区分全库是否存在、候选是否召回、最终是否送达；不存在的证据不放入召回分母 |
| 可用性 | 首次产生有效草稿目标 ≥90%，有限重试后 ≥95% | 报告 n/N 和失败类型。正确表达资料不足可算有效草稿，人工补写不能算模型成功 |
| 答案质量 | 无需实质事实/范围修改的比例目标 ≥80%；指定严重错误在冻结测试内为 0 | 覆盖充分证据题的完整性与缺证题的正确弃答，防止全部弃答刷分；原稿和复核稿分开 |
| 交付 | 支持模板中题目不丢失、非答复内容保留；最终答卷无未处理严重错误 | 部分完成和完整交付分别标注；失败行不能隐藏 |
| 时间 | 记录单题及整表 p50/p95、排队时间、超时和恢复；单题总期限沿用已冻结策略 | 先测整表基线再定客户等待目标，不用 12 题顺序试验承诺 120 题容量 |
| 用户收益 | 真实试点中至少 2/3 可比任务总人工时间减少 30%，最终严重错误不增加，并有再次使用行为 | 建议探索门槛；记录资料整理、上传、审阅、补料和导出的全部人工时间；无参与者不填结果 |
| 成本 | 每份问卷已知生成/embedding/基础设施与人工支持成本可归集；未知部分单列 | 供应商实扣、估算、未知分开；业务成功任务结算不是平台总成本 |

人工时间对照采用当前做法与产品的完整任务比较，尽量匹配题量/难度、交替顺序，记录操作熟悉程度和知识库建设的一次性投入，减少先做一遍后记住答案的偏差。早期小样本报告逐任务结果，不包装成行业省时率。

单一严重失败可以触发修复和重新冻结候选，但不会无限追加调用直到通过。每个候选一次开发对照、一次验证，再决定保留/放弃；若连续两个候选没有改善主要指标，回到资料供给和流程设计，不自动增加更复杂协议。预计需要更多候选时先写明新的假设。

每轮真实调用执行前冻结请求上限与成本预算，并核对当日实际余量。沿用日 200 次生成上限；直接诊断、可能已派发但结果未知的请求与产品调用共同计入，不能以换入口绕过。新增模型评审、优化器、embedding 的额度和费用另列；样本计划不是立即执行全部调用的授权，也不自动扩大既有额度。

## 7. 商业验证与最小经营闭环

### 7.1 先验证需求与使用，再验证付费

访谈关注最近一次真实答卷：收到什么文件、谁找资料、谁批准、花了多少时间、哪里最难、已有工具为何不够、谁能决定采购。先讨论实际经历，再演示产品，避免只收集“看起来不错”。

设计伙伴提供获准使用的资料，必要时采用去标识内容。首轮协助建库，但把建库与人工代填投入单独计时；第二份任务检验是否能减少支持和重复工作。若只有开发者能顺利完成，记录为交付服务依赖，不能宣称自助 SaaS 已成立。

当前没有参与者时继续完成 W0–W4、演示、招募介绍、操作说明、反馈表、试用任务及计时模板。若一个产品周期后仍无参与者，工程状态可以是“可受邀试用”，商业价值状态仍为“未验证”；下一周期优先寻找匹配人群或调整渠道，不以继续堆功能替代。

### 7.2 首版商业形态

推荐先提供“受邀企业工作区 + 有限问卷/题量额度 + 首次资料整理支持”的付费试点，采用现有人工准入和权益管理。内部按成功业务任务计量的机制保留；客户套餐不必直接暴露 token 或模型调用次数。资料摄入、模型失败导致的供应商成本及人工支持仍计入经营成本。

先按完整试用任务核算成本，再形成两种报价假设供客户选择，例如按次试用包和月度有限包；金额不依据未经核实的竞品价格拍定。首个实付由用户通过适合自身经营主体的方式处理，并记录订单/合同与收款回执。实际商户、开票和退款条件确定后再做公开支付集成。

每客户贡献毛利测算：实际收入 − 可归属模型/embedding/存储/服务费用 − 可归属人工交付与支持成本。未知供应商金额单列或给有依据的区间，不当作零。只看到 token 成本低不能说明产品有利润。

### 7.3 阶段决策

| 情况 | 决策 |
| --- | --- |
| 技术与审核闭环可用，但没有匹配客户 | 保持可试用状态，优先招募；不宣布商业完成 |
| 客户主要需要整理资料，自动草稿收益不明显 | 调整为知识整理/答案复用切入，记录服务成本；暂缓自主 Agent 扩建 |
| 大量题资料本来不存在 | 提供可行动的补料清单，验证客户是否愿意补齐；不靠模型编造提高覆盖率 |
| 连续两个匹配客户没有省时、复用或再次使用信号 | 复查任务人群和工作流；停止相同功能扩张，重新选择更具体场景 |
| 真实试点有收益、愿意再用，但尚未付费 | 标为已验证部分使用价值；验证价格/采购与数据要求，不宣称收入成立 |
| 已有真实付费、重复使用且成本可控 | 扩展受邀客户数量；按实测容量调整准入，再讨论公开自助或新场景 |

这些是早期决策信号，不是凭 2–5 个样本证明整个市场的统计门槛。

## 8. 完成定义与工作经历证据

分开记录三项完成状态：

1. **产品交付完成：** 指定范围内可以开户、导入、答复、审核、原表交付、答案复用、支持和退出；失败路径可用，质量与运行证据绑定版本。
2. **试点价值验证完成：** 实际使用者独立完成规定任务，有原始计时/修改/反馈与再次使用记录，明确领域与样本边界。
3. **初步商业验证完成：** 有真实交易或合同交付、成本与支持记录、复购/续用观察；不以口头兴趣替代付费。

它们共同组成完整商业化项目，但可以按阶段形成真实工作成果。在获得真实交易前，经历可描述为“独立开发并运营面向企业问卷响应的产品，完成受邀试点准备/实际试点”，按实际阶段写；获得客户和交易后补充真实结果。项目开发与运营经历可以成立，任职主体、雇佣关系、客户和收入仍按事实陈述。

持续保留的材料控制为：一份产品入口、每个实施工作包的必要任务文件、版本化原始评测/运行数据、客户反馈与经营记录、定期复盘。每次迭代记录“问题—假设—变更—结果—是否保留”，不靠不断增加重复报告体现进度。
