## 当前主机容量实测

采用独立 staging 入口，原本地 CLI 仍拒绝远端对象。执行器在现有 API Pod 运行，绑定 Namespace、实际 Deployment 模板、配置/Secret 哈希、来源字节及执行器 SHA。API 使用 Pod 回环入口，对象使用固定 HTTPS R2 origin，观察器调用正式计量的检索服务。它不是公网端到端延迟测试。

两个新企业各一个有限周期、80 次成功生成额度，合计 160 个计划样本；不延长原 pilot。每轮 ramp 10/并发 1、steady 20/并发 2、burst 40/并发 4、recovery 10/并发 1。总窗口 7,200 秒；上限为 320 模型、4,320 向量、20,000 HTTP 请求，原有全局和租户限制保持。第三个失败后停止新样本，在途样本继续结算。

TXT 59 字节、PDF 678 字节、DOCX 36,618 字节，均为一块合成事实。结果不能外推为大文档容量。

| 结果 | 数值 |
| --- | --- |
| 完整流程通过 | 9 / 160 |
| 已启动但失败 | 4 / 160 |
| 未执行 | 147 / 160 |
| 上传 p95 | 18,699.7 ms；目标 5,000 ms 未满足 |
| 解析 p95 | 21,350.0 ms；已观测样本满足 30,000 ms，但剩余样本未完成 |
| 检索 p95 | 5,558.6 ms；目标 2,000 ms 未满足 |
| 生成受理 p95 | 5,688.6 ms；目标 250 ms 未满足 |
| 生成与恢复 p95 | 180,001.3 ms；目标 180,000 ms 未满足 |

四次失败分别为上传超时、一次生成过期和两次采样终态超时。后来只读核查显示两次超时任务最终成功；原始采样仍计失败，不能事后改成在时限内通过。最终 12 个生成 attempt 中 11 成功、1 过期；模型调用 18 次（11 成功、6 上游错误、1 结果未知），向量 36 次均返回。未知请求成本不填零，也不重新提交过期任务。

同期 45 次资源采样全部获得有效观察：CPU 峰值约 9.76%，主机可用内存最低 1,433,681,920 字节。后续五次数据库 `SELECT 1` 往返约 51.4–51.6 ms，三次认证会话 GET 约 239–291 ms。这些数据说明此次失败不能直接归因于 CPU/内存耗尽；完整容量目标仍为 **未通过**，需要修复供应商稳定性和请求链路延迟后以新计划复测。

## 金额和最终审核

用户随后明确要求评估原指标而非机械卡住验收。新的[用户体验验收](user-experience-acceptance.md)将 250 ms 用于即时界面反馈，另设受理优化目标与有界恢复；供应商异常通过备用时间预留、相同请求标识、状态恢复和准确计费处理。以上历史实测不改写，工程候选和线上容量复测分别记录。

模型供应商的 `/api/usage/token/` 返回累计配额单位且标记无限配额，没有币种、期间或逐笔金额。向量供应商 `/v1/user/info` 返回 410，并明确端点已退役。只读核查没有调用生成或向量接口；不能把账户余额/配额单位当作本批费用。

最终验收仍需要：实际供应商金额记录、独立业务/发布审核，以及明确的按需恢复目标和整机演练。当前 Windows 调度依赖本机在线和登录；本地应用快照恢复也不代表整机 RPO≤300 秒/RTO≤1800 秒已通过。用户的操作授权已经有效，以上缺口不是再次等待相同权限。

用户可按[最终验收入口](final-project-acceptance.md)检查已生成 Agent 结果、原售前复核及 CSV；不需要为了重复 OAuth 或寻找历史任务再次生成。
